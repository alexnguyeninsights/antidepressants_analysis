# Machine Learning for Antidepressant Adverse Event Classification

## Project Overview

Adverse drug event reports contain useful safety information, but the data are large, messy, and difficult to review manually.

This project explored whether machine learning and natural language processing could help organise antidepressant-related adverse event reports and identify possible safety patterns using the FDA Adverse Event Reporting System (FAERS).

The main work was not only building a model. A large part of the project involved understanding how FAERS data tables link together, cleaning duplicated or incomplete records, mapping adverse event terms into standard MedDRA categories, and preparing the data for analysis.

This project was completed as my master's final project and has been adapted into a portfolio case study to demonstrate data cleaning, table linking, clinical text classification, model comparison, statistical analysis, and communication of complex public health data.

## Why This Project Matters

FAERS is a real-world public health dataset. It is not provided as one clean table, and it includes many of the challenges found in workplace data projects:

- large file sizes

## Data Source

The project used the FDA Adverse Event Reporting System (FAERS), a public database containing adverse event reports submitted to the U.S. Food and Drug Administration (FDA).

FAERS includes information such as:

- patient demographics
- reported medications
- indications or reasons for drug use
- adverse event terms
- outcomes
- report sources

For this project, I focused on antidepressant-related adverse event reports from 2018 to 2023.

## Data Structure

FAERS is made up of multiple linked files rather than one clean table.

| FAERS table | Plain-English meaning |
|---|---|
| DEMO | Patient and report details |
| DRUG | Medication information |
| INDI | Indication or reason for drug use |
| REAC | Reported adverse event terms |
| OUTC | Outcome information |
| RPSR | Report source |

These files were linked using report identifiers such as `primaryid` and `caseid`.

One key learning from this project was that understanding the data structure came before modelling. Before I could classify adverse events, I needed to understand what each table represented, how records linked together, and what the final cleaned dataset actually meant.

## Cleaning Decisions

| Cleaning step | Why I did it | Decision basis |
|---|---|---|
| Removed deleted reports | Deleted FAERS reports should not be included in analysis | FAERS deletion file |
| Kept latest case version | FAERS cases can be updated over time | Reduce double-counting of older case versions |
| Filtered antidepressant-related records | The project focused on antidepressant adverse events | Drug name and antidepressant class matching |
| Focused on patients aged 12+ | Aligned with the project scope and antidepressant-use context | Research/project design decision |
| Mapped adverse event terms to MedDRA System Organ Classes | Raw adverse event terms are detailed and inconsistent | Standard medical classification structure |
| Curated final analysis dataset | Prepared records for consistent classification and interpretation | Required fields for modelling and analysis |

Cleaning was not only a technical step. It required judgement about what records should be included, what assumptions were reasonable, and how the final dataset should be interpreted.

## Methods

### 1. Data preprocessing

The preprocessing stage included:

- downloading FAERS quarterly files
- merging relevant source tables
- removing deleted or duplicated records
- keeping the latest case versions
- filtering for suspected antidepressant records
- preparing text fields for classification
- mapping adverse event terms to MedDRA System Organ Classes

### 2. Exploratory data analysis

The EDA stage explored:

- adverse event category distribution
- antidepressant class patterns
- age and gender patterns
- time trends across pre-COVID, during-COVID, and post-COVID periods

### 3. Feature engineering

Feature engineering included:

- creating TF-IDF vectors from adverse event text
- creating COVID-period labels
- preparing mapped adverse event categories as target labels
- preparing cleaned text for traditional machine learning and Clinical-BERT models

### 4. Modelling

The project compared:

- Logistic Regression with TF-IDF features
- Support Vector Classifier with TF-IDF features
- Clinical-BERT for advanced text classification

### 5. Topic modelling and statistical analysis

Additional analysis included:

- LDA topic modelling to explore emerging adverse event themes
- disproportionality analysis using Proportional Reporting Ratio (PRR)
- disproportionality analysis using Reporting Odds Ratio (ROR)

## Key Results

The project found that:

- Clinical-BERT produced the strongest classification performance in this experiment.
- Logistic Regression and Support Vector Classifier provided lighter-weight alternatives for adverse event categorisation.
- Topic modelling helped identify adverse event themes across the study period.
- Disproportionality analysis provided an additional way to explore potential adverse event reporting patterns.
- The project highlighted the importance of data cleaning, table linking, and careful interpretation before modelling.

---

## Model Performance Note

Clinical-BERT achieved the strongest performance in this experiment. However, very high model performance should be interpreted carefully.

Further validation would be needed to check for:

- duplicated or highly similar reports across train and test sets
- class imbalance effects
- whether label mapping made the classification task easier
- performance on a later unseen time period
- model explainability and clinical interpretability

This is an important learning point from the project: strong model results are useful, but they should still be questioned, validated, and communicated carefully.

---

## Limitations

This project is exploratory and should not be interpreted as clinical evidence.

Key limitations include:

- FAERS reports can support signal exploration, but they do not prove causation.
- Reporting frequency may be affected by public awareness, media attention, COVID-era health system changes, and reporting behaviour.
- Drug names may appear in different formats, so antidepressant filtering may not capture every relevant case.
- Mapping adverse event terms to broader MedDRA categories improves consistency but may reduce clinical detail.
- Very high model performance requires further validation before any real-world use.
- The project was completed as an academic research-style project, not as a deployed clinical decision-support system.

## How to Run

Due to the size of the FAERS data, the full raw dataset is not stored directly in this GitHub repository.

To rerun the project:

1. Clone this repository.
2. Install the required Python libraries.
3. Download the required data files using the instructions in `0b. data_re-run_guideline.md`
4. Run the notebooks sequentially from Step 1 to Step 7.
5. Review row counts and outputs after each major step.
  *Note: Step 5 model training is computationally intensive. In the original project environment, this step took several hours to complete.*

---

## Rerun / Backfill Guide

To rerun or backfill the project for a new FAERS period:

1. Add the new quarterly FAERS files to the raw data folder.
2. Check that the file naming convention and table structure match the expected FAERS format.
3. Run notebooks in order from Step 1 to Step 7.
4. Review row counts after each major step.
5. Confirm deleted reports and latest case versions are handled.
6. Compare output counts against the previous run.
7. Update the README, report, and visual outputs with the new results.

This section is included because repeatability is important in workplace data settings. A project should not only show what was done once; it should also explain how the process can be repeated.
